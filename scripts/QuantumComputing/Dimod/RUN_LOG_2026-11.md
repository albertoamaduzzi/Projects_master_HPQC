# QPU run log, November 2026: what was launched, what it changed, what it showed

All commands were run on Windows (PowerShell) from `scripts\QuantumComputing\Dimod\src\unlearnable_games_explanation`, with `$F = "results\sk"`. QPU time came from the Cineca Leap project (`CINE`). Its allocation ran out on 3 November during the last experiment.

There were two kinds of experiments:

- **The main experiment** (`results\sk`): the QPU acting as the central planner on the SK game. It covers 4 problem classes and N = 8…160 on both machines.
- **The side experiments** (`results\ta2`, `ta20`, `ta200`, `ext20`, `pgs`): the same pure-SK instances run under different settings: annealing time, coupler range, number of reads. They measure **how the hardware behaves**. Their results explain the main experiment's results, but they don't replace them.

## 2. What each experiment showed

### 2.1 Main experiment, N ≤ 24 (`report`)
Every row was `reached = True`. Both QPUs found the **exact** optimum of every instance, in all 4 classes, at N = 8, 16, 24. At N = 24 that is 1 of 2^23 ≈ 8.4 million configurations, and the raw best read was already optimal. Small problems are easy for the QPU. The comparison with the classical solvers and the game, and the large N, come from `compare` once the classical stage has run (§4).

### 2.2 Chain strength (#8, #11): zero broken chains is too strict at large N

| rule | Zephyr p_opt | Pegasus p_opt |
|---|---|---|
| 0 broken chains in 200 reads (used by the main run) | 0.75–3 up to N = 64; **6 (grid edge) for N ≥ 72** | **6 (grid edge) for N ≥ 56** |
| ≤ 1 % of the chains broken | 0.75–1.414 up to N = 80; 2 at N = 88–104 | 1–2 up to N = 120; 3 at N = 128–160 |

At N = 104 one call has 104 chains × 200 reads = 20 800 chain readings. A break rate of 1 in 10 000 already fails the zero-break rule. Requiring zero pushed p to 6, the most compressed setting. Allowing 1 % breaks needs only p ≈ 2–3. Pegasus needs larger p than Zephyr at every N: its qubits have fewer couplers (15 vs 20), so its chains are longer.

### 2.3 Annealing time and coupler range (#12, #13): 3 pure-SK instances, 500 reads

The gap is the mean (R_best known − R_QPU raw) / R_best known. The best known is the best polished read of all runs. Above N = 24 no exact reference exists.

| setting | Zephyr N = 64 (p = 3) | Pegasus N = 64 (p = 6) | Zephyr N = 104 (p = 6) | Pegasus N = 104 (p = 6) |
|---|---|---|---|---|
| 2 µs | 2.0 % | 30.3 % | 33.6 % | 44.7 % |
| 20 µs (default) | 0.6 % | 23.1 % | 31.0 % | 40.8 % |
| 200 µs | 0.5 % | 21.9 % | 27.9 % | 27.6 % |
| 20 µs + extended range | 0.1 % | 26.2 % | 33.0 % | 41.2 % |
| chain breaks (fraction of chains, 20 µs) | 0.000 | 0.001 | 0.000 | 0.003 |

**1. Compression decides the quality.** The programmed rms of an SK coupling is 1/(p·√(N−1)), and the relative control error is ε = σ·√|E|·p·√(N−1) (σ = 0.02, |E| = 1.1):

| case | programmed rms | ε | gap at 20 µs |
|---|---|---|---|
| Zephyr N = 64, p = 3 | 1/(3 × 7.94) = 0.042 | 0.50 | **0.6 %** |
| Pegasus N = 64, p = 6 | 1/(6 × 7.94) = 0.021 | 1.00 | **23 %** |
| Zephyr / Pegasus N = 104, p = 6 | 1/(6 × 10.15) = 0.016 | 1.28 | **31–41 %** |

The quality drops exactly where the feasibility model puts ε ≈ 1. At ε ≈ 0.5 the raw reads are nearly optimal. At ε ≥ 1 they are 20–45 % below. The same N = 64 on two machines, with p = 3 vs p = 6, shows it directly: 0.6 % vs 23 %. Zephyr's better quality is mostly its smaller p.

**2. Slower anneals help only where the problem is hard.** From 2 to 200 µs the gap shrinks a little at N = 64 Zephyr (2 % → 0.5 %), and a lot at N = 104 Pegasus (45 % → 28 %). Part of the loss is dynamics (freeze-out too early). Even at 200 µs, though, the large-N gap stays at 22–28 %, so most of it is noise and compression, which time cannot fix.

**3. The extended range did not help.** The changes against 20 µs are within the spread between instances: +0.5 % to −4 %. The chain-break fractions are also identical to the 20 µs run. That suggests the extended range may **not have been applied**: the code falls back to normal scaling when a solver does not offer it. Check with #A4 below before drawing a conclusion.

**4. Polishing recovers the rest.** Greedy descent from the QPU reads reached the same best-known reward on every machine and setting, but that is classical work. The raw reads measure the QPU; the polished reads measure QPU + CPU.

### 2.4 Many reads at small N (#14, partial)
With 6171 reads per call, both machines returned the same best reward on every instance at N = 8, 12, 16, which is almost certainly the exact optimum (`compare` checks it). At N = 12 on Zephyr with the interpolated p = 0.875, 1.9 % of chains broke in one instance. These reads are the best data for `noise-fit`, which measures σ and β_eff, and for P(exact) per read against N. Only N ≤ 16 is complete on both machines.

## 3. What this amounts to
Partly, yes, these were tests of the solver on different hardware. More precisely, they measured **where the QPU stops being a faithful planner**:
- **Small N, low compression (ε ≲ 0.5):** exact or nearly exact optima.
- **Large N:** the chains need p ≈ 2–6, and the SK couplings shrink to 1.6–4 % of the full range. The control error is then as large as the couplings, and the raw answers fall 20–45 % short.
- **Longer anneals help a little.** The extended range, as run, did not help measurably.
- **Pegasus is worse than Zephyr** at the same N, because it needs longer chains and therefore a larger p.
